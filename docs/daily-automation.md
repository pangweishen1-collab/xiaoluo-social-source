# 小骆日报云端自动化

## 当前实现与边界

北京时间每天 11:00，`xiaoluo-daily-generator` 从网站热点榜读取候选原文，重新抓取发布者网页，要求原网页提供可核对的发布日期、具体正文和支持事实的原句。最多向独立复核服务提交 3 条近期事件；没有合格候选时也提交失败记录，不编造内容。

北京时间每天 11:15，已有稳定运行的热点榜 Worker 通过另一条 Cron 检查当天 `daily_automation_runs`。只有确认**没有**当天记录，才通过私有 Service Binding 补调生成器；`published`、`rejected` 和 `skipped_existing` 都不重跑。若数据库状态无法读取，兜底直接报错，不在不确定状态下重复生成。发布器仍负责同日不覆盖与重复事件拦截。两条 Cron 都由 Cloudflare 承载，独立 Worker 调度可降低单条触发器漏跑风险，但不能保证平台故障时一定运行。

`xiaoluo-daily-reviewer` 不接收生成器的自报 `verified`：它重新抓取原文，核对原句与原文日期，使用单独一次 Workers AI 调用核对中文标题、摘要、产品身份、事件时效与社交／语聊／直播相关性。只要一条未通过，整期不发布。复核服务没有生产数据库绑定，只能通过私有 Service Binding 调用发布服务。

`xiaoluo-daily-publisher` 没有 AI 或公网入口，仅接收复核服务的内部调用。它再验证日期、来源地址、事实与文案一致性，生成三栏结构化版面、Markdown 和微信纯文本，检查生产库中是否已有同日或重复事件，最后用 D1 事务写入公开日报和私有运行记录，并回读。今日若已有人工日报，不自动覆盖。失败草稿保存在私有 `daily_automation_runs.draft_json` 中，公开接口只提供状态，管理员登录后才能读取草稿与原因。

这是“**达到核验条件时自动发布**”，不是保证每天硬凑一期。当前采集只覆盖热点榜中有原始网页、日期和实质变化的近期资讯，自动条目只会进入第三栏「语聊直播产品近一周变化」。前两栏「产品雷达」「团队与招聘动向」目前尚无符合小骆 Skill 证据规则的云端采集器；空栏明确显示暂无可核验条目。今后要扩展这两栏，应先接入有日期、市场／商店／榜类／名次的榜单快照，以及能确认仍开放的原始招聘页，分别补齐核验和回归测试。不能把热点榜标题改名塞入这两栏。

## 部署及验收

1. 对已确认的生产 D1 执行一次 `db/daily-automation.sql`；保留现有 `daily_reports` 内容，不做覆盖或删除。
2. 先部署 `wrangler.daily-publisher.json`，再部署 `wrangler.daily-reviewer.json`。两者均设置 `workers_dev:false`，没有公开路由。生成器仅绑定复核服务；复核服务仅绑定发布服务；只有发布服务有 D1 权限。
3. 在生成器尚无定时触发的情况下，用真实来源进行演练，分别确认独立复核通过、拒绝、重复日期、原文不可达和无候选的行为；失败只产生私有草稿。生产当天若已有日报，只验证“跳过同日”而不覆盖。
4. 先部署生成器的私有补跑入口，再部署 `wrangler.hot.json` 中 `15 3 * * *`（UTC）备用触发器和 `DAILY_GENERATOR` 绑定；原热点榜 `0 0 * * *`（UTC）保持不变。生成器原有 `0 3 * * *`（UTC）对应北京时间 11:00，备用触发器对应 11:15。检查两项线上 Cron 配置，并在次日分别核对实际调用记录与 `/api/daily-automation-status`，不能仅凭部署成功判定定时已运行。
5. 异常通知在北京时间每天 11:35 检查当天状态：`rejected`、无当日运行记录或接口不可用时通知；`published` 和已有人工日报导致的 `skipped_existing` 保持安静。公开状态接口不返回草稿正文；管理员可从 `/api/daily-automation-drafts` 查看拒绝原因和私有双格式文本。

Cloudflare Workers AI 目前采用 `@cf/meta/llama-3.3-70b-instruct-fp8-fast`，生成器每期最多 4 次调用，复核最多 3 次调用。AI 误判可能发生，因此模型输出还要经过原句、原日期、重复来源、结构和写库回读等硬规则；不确定时拒绝。Cloudflare AI 有用量配额和按量计费规则，部署后应观察账户实际用量与失败率。
