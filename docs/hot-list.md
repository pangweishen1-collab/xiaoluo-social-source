# 小骆社交热点榜

热点榜每天北京时间 08:00 由 `wrangler.hot.json` 的定时任务重新采集。11:15 的另一个任务只为日报兜底，不能用于刷新热点榜。

## 采集与解读

- `shared/hot-list.mjs` 登记可读取的官方/媒体源。核心产品的 Apple lookup 固定 App ID、名称和市场，只读取版本说明，不以产品介绍冒充版本变化；泛化修复不入榜。
- JOYY IR 与官方新闻稿发行组织（GlobeNewswire 23553）同属一个发布者。赤子城的公司新闻 JSON 有全文，RSS 的短描述仅作发现线索。
- `worker/hot-enrichment.ts` 在标题筛选之前为有限数量的核心公司候选读取原文。只在具体社交经营数据或产品变化有正文依据时接受通用财报标题。
- 赤子城投资者关系中的港交所 PDF 由私有正文服务进行文字提取（不生成图片描述），同时核对公司名、股票代码 9911、公告路径日期、董事会落款日期和官方索引日期；财报统计期不能冒充公告日期。文件上限 2 MiB，完整提取结果只在内存核对，正文最多保留 18,000 字符供本次提炼和复核使用。
- 每条榜单通过私有 `xiaoluo-hot-detail` 服务提炼中文标题、具体变化、分析性关注理由及短原句。Qwen 生成中文、Llama 独立复核；模型从程序预提取的原句编号中选择证据，不自行改写原句。再次核对身份、日期、数字、指控/测试/计划状态；失败不展示未通过文案。
- 同时核对事件时效：新文章重述明确在 90 天前发生的产品动作不会成为新热点；新财报披露的历史比较期间、新诉讼披露的历史行为不等于旧事翻炒。生成与复核均收到当前日期，历史公告不以今天的未来语态讲述。
- 正文处理使用服务绑定，避免把所有信源、原文和模型调用放在单次采集请求的外部请求额度里。网页 API 不运行 AI，只读取 D1 快照和短缓存。
- 完整正文仅存在于本次处理内存；公开快照保存短解读、原题、来源和原句，不保存全文。原文日期与抓取日期分别保留。
- 证据候选只在主体或官方社交经营指标附近选择连续片段，复用已规范化的正文与匹配器，避免对长篇公告逐词重复扫描全文；最终字面校验、引用长度与独立复核门禁不变。

## 快照与容错

D1 `hot_list_snapshot` 的 `id=1` 保存 v9 JSON。旧 v7/v8 的原文链接只可重新筛选，不直接作为 v9 快照使用。已核验详情复用必须匹配原始来源、原题和发布日期；商店同链接的新版本不会继承旧版解读。

## 增量处理与额度保护

发布前先执行 `db/hot-event-processing-cache.sql` 创建私有缓存表。它与公开榜单、日报草稿分离，处理器不在请求中建表。缓存只保存正文 SHA-256 指纹、版本、已核验的短解读或拒绝结论，不存全文和未通过提案。

每次仍读取最新正文，指纹包含规则版本、主题、来源身份、URL、原题、原文日期及规范化正文。命中时直接复用已核验结果，保留原核验时间，不再调用生成或复核模型。正文、商店版本、日期或规则变化后重新处理；升级提取/筛选/提示词/核验规则时必须升级 `HOT_PROCESSING_VERSION`。未读取正文不得仅凭 URL 判断未变化。

相同正文的明确拒绝也缓存 90 天，变化后重试；网络失败不作为永久拒绝。按主键读取所需条目，不全量加载历史缓存。每轮默认最多处理 10 个未命中事件，已命中内容不占预算；后续真实候选仍受 20 次尝试总上限约束。两阶段 AI 核验不变，公开页面刷新不调用 AI。

增量任务串行调用 AI，发现 4006/429 等额度错误立即停止该轮后续 AI 请求，并持久暂停最多一小时（若更早到达下个 UTC 日则至其后一分钟）。暂停结束仅允许后续正常任务探测，不自动重跑；已有合格缓存仍可复用。30 分钟的令牌锁防止预览与定时任务重复处理，失败释放；数据库不可确认时先停止，不按全量未命中重新花额度。预算/额度不足只延后处理，不伪造拒绝或核验成功。

榜单近期事件与较早的持续观察分组，总数最多 10 条。正式排名只包含正文核验通过的详情，不合格原文只进入观察候选；从本次已采集的真实原文继续补选，最多尝试 20 个事件。合格不足 10 条如实显示，零条通过时不覆盖现有快照。正文或 AI 暂时失败可以保留同原题/日期的上次合格解读并标注核验时间，核验明确拒绝则不沿用。

公开接口不为凑足十条用未经 AI 核验的即时标题替换一份较短的合格榜单。若定时快照超过 24 小时仍未更新，保留其真实时间并标识沿用上期，不伪造最近抓取时间。

## 发布和验收

1. 运行 `pnpm run check`，检查原文提炼、来源身份、历史恢复、拒绝文案不泄漏和真实 React 渲染测试。
2. 先对生产 D1 执行 `db/hot-event-processing-cache.sql`，再部署 `wrangler.hot-detail.json` 的私有正文服务、`wrangler.hot.json` 的定时采集器，最后构建/发布 Pages。所有服务均不启用 workers.dev；正文服务没有 D1 或发布权限。
3. 私有采集器 `POST /__hot-preview` 运行相同采集/提炼流程并返回候选快照，写入私有处理缓存但绝不写公开榜单；只可由同账户服务绑定或已认证 Wrangler 远程预览调用。日志汇总命中、拒绝复用、新处理、延后和额度暂停计数，不打印全文或拒绝文案。
4. 受控触发 `cron=0 0 * * *` 后，以 D1 时间、公开 `/api/hot-list` 的 v9/条数/详情和线上页面验收。回调超时不能作为成功依据。
5. 当前浏览器/边缘缓存约 5 分钟，缓存键按方法版本区分；发布时确认新版页面请求 `method=9`。

人工验收发布也可使用 `node scripts/publish-reviewed-hot.mjs <候选.json> --confirm-production` 保存**确切已审核候选**，避免重新运行模型换成另一份结果。脚本要求 30 分钟内的十条 ready、来源/日期校验通过、无全文或草稿提案，去掉私有诊断后写库，再回读 D1 核对时间和 SHA-256；写入被跳过或内容不一致均报错。还须核对公开 API 和页面，不以命令退出为最终验收。

不要把核验通过理解为不可出错，也不要把来源读取成功理解为发现了新事件。保留可追溯原文及用户能辨别的事实、分析、历史日期。
